# Проверка кластера: девять сценариев

Порядок не случаен. Каждый следующий опирается на то, что предыдущий уже
подтвердил, и первое же расхождение отсекает половину возможных причин. Если
времени мало — сценарии 1, 2 и 4 дают костяк: кластер собрался, обе машины
считают, данные между ними ходят.

Все скрипты кладутся в форму «точка входа» на странице Ray. Запускается такой
скрипт **только на ранге 0** — остальные ранги просто держат свои узлы; так и
задумано, потому что `ray.init()` на ранге 0 распоряжается всем кластером.
Результат смотреть в логе задачи ранга 0.

Где сценарий требует карт, это сказано отдельно. Остальные считаются и на
процессоре.

---

## Пролог, общий для всех скриптов

Дальше он подразумевается вставленным в начало. Две строчки в нём не
косметические.

```python
import ray
# Явным импортом: одного `import ray` для этого подмодуля не хватает, и
# обращение через ray.util.… падает с AttributeError.
from ray.util.scheduling_strategies import NodeAffinitySchedulingStrategy

ray.init()

def на(узел):
    """Положить задачу именно на этот узел, а не куда планировщик решит."""
    return NodeAffinitySchedulingStrategy(node_id=узел, soft=False)

def узлы_по_рангам():
    """Узлы в порядке рангов.

    Через адреса, а не через порядок ray.nodes(): тот ничем не задан, и
    «первый в списке» — это не голова, а как повезёт. Зато адрес ранга N по
    построению равен 127.0.0.<N+2> и означает одно и то же на всех машинах.
    """
    живые = {n["NodeManagerAddress"]: n["NodeID"]
             for n in ray.nodes() if n["Alive"]}
    по_рангам = [живые.get(f"127.0.0.{2 + ранг}") for ранг in range(len(живые))]
    if None in по_рангам:
        raise SystemExit(f"узлы записаны не своими адресами: {sorted(живые)}")
    return по_рангам
```

Последняя проверка полезна сама по себе: если она сработала, значит на узле
старый payload, и всё остальное можно не запускать.

## 1. Кластер собрался и держится

**Зачем.** Пока это не подтверждено, любая другая неудача может оказаться этой.

**Как.** Поднять кластер из двух узлов без скрипта. В логе каждого ранга
дождаться:

```
ранг N/2 в кластере, узлов 2, голова 127.0.0.2:NNNNN
узлы в кластере: <id> 127.0.0.2:NNNNN alive=True; <id> 127.0.0.3:NNNNN alive=True
```

**Что смотреть.** Оба адреса — из `127.0.0.x`. Если там `192.168.*` или `10.*`,
узел записался адресом своей локальной сети, недостижимым с чужой машины, и
через полминуты голова объявит его мёртвым.

**Через десять минут** открыть консоль ещё раз: в группе по-прежнему два узла.
Кластер разваливался именно так — собирался, а через тридцать секунд терял узел.

---

## 2. Обе машины действительно считают

**Зачем.** «Кластер собрался» и «работа раскладывается по узлам» — разные
утверждения. Второе и есть то, за что платит клиент.

```python
import collections, os, socket, time

print("ресурсы кластера:", ray.cluster_resources())

@ray.remote(num_cpus=1)
def кто_я(_):
    time.sleep(1)          # иначе всё успеет лечь на первый освободившийся узел
    return socket.gethostname(), os.environ.get("LOOMA_RANK")

где = collections.Counter(ray.get([кто_я.remote(i) for i in range(20)]))
for узел, сколько in где.items():
    print(f"{узел}: {сколько} задач")
```

**Что смотреть.** В `cluster_resources()` — `CPU` как сумма долей обоих узлов.
`GPU` появится, только если в форме указано «карт на ранг» больше нуля. В
разбивке — оба узла.

**Если всё на одном узле.** Сравните доли CPU: если одному досталось заметно
больше, планировщик честно сложит работу туда. Это не поломка — запустите
задач больше, чем ядер у одного узла.

## 3. Библиотеки клиента приехали на каждый узел

**Зачем.** Окружение ставится на каждом узле отдельно. Приехавшее на голову и
не приехавшее на второй выглядит как ошибка в коде клиента.

**Как.** В поле «библиотеки» вписать столбиком:

```
numpy
```

```python
@ray.remote
def проверить():
    import numpy, os, sys
    return os.environ.get("LOOMA_RANK"), numpy.__version__, sys.version.split()[0]

for ранг, версия, питон in ray.get(
        [проверить.options(scheduling_strategy=на(узел)).remote()
         for узел in узлы_по_рангам()]):
    print(f"ранг {ранг}: numpy {версия}, python {питон}")
```

**Что смотреть.** Строка на каждый узел, версия одна и та же.

**Если `ModuleNotFoundError`** — библиотека не доехала до этого узла; смотреть
лог его задачи на стадии установки окружения.

## 4. Данные ходят между узлами, и вот с какой скоростью

**Зачем.** Это единственное число, по которому потом решается, поедет ли на
кластере конкретная стратегия. Всё остальное — следствия.

```python
import time, numpy

свой = ray.get_runtime_context().get_node_id()
дальний = next(у for у in узлы_по_рангам() if у != свой)

@ray.remote(scheduling_strategy=на(дальний))
def принять(кусок):
    return кусок.nbytes

for мб in (1, 8, 64):
    ссылка = ray.put(numpy.zeros(мб * 1024 * 1024, dtype=numpy.uint8))
    начало = time.time()
    ray.get(принять.remote(ссылка))
    ушло = time.time() - начало
    print(f"{мб:>3} МБ за {ушло:5.2f} с = {мб * 8 / ушло:6.1f} Мбит/с")
```

Требует `numpy` в поле «библиотеки».

**Что смотреть.** Число на 64 МБ — рабочая полоса между узлами. Малые куски
меряют задержку, а не полосу, и будут заметно хуже: это нормально.

**Как этим пользоваться.** Обучение модели на 7B через DDP требует около 14 ГБ
обмена **на шаг**. Поделите на полученное число — получите время шага. Вышли
минуты — значит эта стратегия здесь бессмысленна, и инженерией это не лечится.

## 5. Межузловой обмен своими руками

**Зачем.** Не всё выражается через Ray. Клиенту нужен способ связать узлы своим
кодом — для этого у него есть окно портов, проброшенное заранее.

Каждый ранг получает в окружении:

| Переменная | Что в ней |
|---|---|
| `LOOMA_RANK_ADDRS` | `0=127.0.0.2,1=127.0.0.3` — где какой ранг |
| `LOOMA_PORTS` | `20170-20199` — порты ЭТОГО ранга, видные соседям |
| `MASTER_ADDR` / `MASTER_PORT` | точка встречи на ранге 0 |
| `WORLD_SIZE`, `RANK`, `NODE_RANK` | размер группы и своё место в ней |

Адреса `127.0.0.x` — не локалхост в обычном смысле: у каждого ранга свой, и он
означает одно и то же на всех машинах группы. У себя за ним настоящий процесс,
на других машинах — агент с туннелем.

```python
import os, socket, time

адрес, порт = os.environ["MASTER_ADDR"], int(os.environ["MASTER_PORT"])
ранги = узлы_по_рангам()

@ray.remote(scheduling_strategy=на(ранги[0]))
def слушать():
    сервер = socket.socket()
    сервер.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    сервер.bind((адрес, порт))     # свой адрес ранга 0, а не 0.0.0.0
    сервер.listen(1)
    сервер.settimeout(60)
    гость, _ = сервер.accept()
    было = гость.recv(64)
    гость.sendall(b"ok:" + было)
    return было.decode()

@ray.remote(scheduling_strategy=на(ранги[1]))
def постучаться():
    time.sleep(3)                  # дать слушателю встать
    свой = socket.create_connection((адрес, порт), timeout=30)
    свой.sendall(b"privet")
    return свой.recv(64).decode()

ждём = слушать.remote()
print("гость получил:", ray.get(постучаться.remote()))
print("хозяин получил:", ray.get(ждём))
```

**Что смотреть.** `гость получил: ok:privet` — соединение прошло между машинами
через туннель, и клиентский код может строить на этом что угодно.

**Если соединение отвергнуто** — порт вне окна. Сверьтесь с `LOOMA_PORTS` того
ранга, который слушает. Порты вне окна прекрасно работают у себя на машине и не
видны снаружи, поэтому ошибка появляется только на двух узлах.

## 6. torch.distributed: где именно проходит граница

**Зачем.** Чтобы не выяснять это на клиенте. Граница настоящая, и она не в
нашем коде.

Требует `torch` в поле «библиотеки».

### Что работает — точка встречи

`TCPStore` живёт на одном порту, и он проброшен.

```python
import os
from datetime import timedelta
import torch.distributed as dist

адрес, порт = os.environ["MASTER_ADDR"], int(os.environ["MASTER_PORT"])
ранги = узлы_по_рангам()
СРОК = timedelta(seconds=60)

@ray.remote(scheduling_strategy=на(ранги[0]))
def хозяин():
    склад = dist.TCPStore(адрес, порт, 2, True, timeout=СРОК)
    склад.set("привет", "от нулевого")
    return склад.get("ответ").decode()

@ray.remote(scheduling_strategy=на(ранги[1]))
def гость():
    склад = dist.TCPStore(адрес, порт, 2, False, timeout=СРОК)
    значение = склад.get("привет").decode()
    склад.set("ответ", "от первого")
    return значение

ждём = хозяин.remote()
print("гость прочитал:", ray.get(гость.remote()))
print("хозяин прочитал:", ray.get(ждём))
```

Через такой склад строится параметр-сервер и любой обмен с редкой
синхронизацией.

### Что НЕ работает — коллективы между машинами

`init_process_group` с backend `gloo` или `nccl` дойдёт до точки встречи и
повиснет на первом `all_reduce`. Причина не в настройке: коллективы открывают
между рангами свои сокеты на **случайных** портах, и какой порт им достанется,
известно только после того, как они его заняли. Пробросить заранее то, что ещё
не выбрано, нельзя. Лечится это не флагом, а сетевым слоем другого рода —
общим адресным контуром на всех узлах; такого слоя сейчас нет.

**Внутри одной машины коллективы работают полностью.** Выберите один узел и
поставьте на него два ранга: там `127.0.0.1` настоящий.

**Вывод для клиента.** Между машинами — Ray-native обмен (сценарий 4) или свой
транспорт (сценарий 5). Внутри машины — что угодно.

## 7. Задача, которая не влезает в одну карту

Требует карт на обоих узлах.

**Зачем.** Это вопрос, который задаёт каждый: «у меня 40 ГБ, а карты по 24».
Сценарий показывает и ответ, и его цену.

Ray **не** объединяет VRAM: одна аллокация CUDA не лежит на двух машинах — как
и на одной машине с двумя картами. Разрезать должна стратегия. Работающая здесь
стратегия — конвейер по слоям: между узлами едут активации, а не веса.

```python
import time, torch

@ray.remote(num_gpus=1)
class Половина:
    def __init__(self, слоёв, ширина):
        self.блок = torch.nn.Sequential(*[
            torch.nn.Linear(ширина, ширина) for _ in range(слоёв)]).cuda().half()
    def вперёд(self, x):
        with torch.no_grad():
            return self.блок(x.cuda().half()).cpu()

ширина, слоёв = 4096, 8
ранги = узлы_по_рангам()
первая = Половина.options(scheduling_strategy=на(ранги[0])).remote(слоёв, ширина)
вторая = Половина.options(scheduling_strategy=на(ранги[1])).remote(слоёв, ширина)

x = torch.randn(8, 2048, ширина)
начало = time.time()
итог = ray.get(вторая.вперёд.remote(первая.вперёд.remote(x)))
print(f"через обе половины за {time.time() - начало:.2f} с, форма {tuple(итог.shape)}")
```

**Что смотреть.** Оба актора заняли по карте — значит модель размазана по двум
машинам и суммарная память использована. Время прохода включает переезд
активаций: поделите их объём на число из сценария 4 и сверьтесь.

**Чего сценарий не показывает.** Обучение. Оно добавляет обратный проход, то
есть примерно удваивает обмен. Конвейерное обучение на этом канале возможно при
большом накоплении градиента; DDP и FSDP — нет, и сценарий 4 объясняет почему.

**Честно:** из девяти этот проверен меньше остальных. Если не пойдёт, дело
скорее в torch и картах, чем в кластере, — и сценарии 2 и 3 к тому моменту это
уже разделят.

## 8. Кластер переживает нагрузку и снятие

**Зачем.** Аренда — это часы, а не минуты. Разваливалось оно как раз со
временем.

1. Оставить кластер под нагрузкой — например, повторять сценарий 4 по кругу.
2. Через полчаса открыть консоль: в группе по-прежнему оба узла.
3. Снять группу кнопкой. Задачи уходят в `stopped`, на машинах не остаётся
   процессов Ray.

**Что смотреть в логе агента.** Строки «туннель … прожил N с и закрылся».
Долгие соединения несущие: на них держится связь узла с головой. Если такое
закрывается регулярно через одинаковое N — это срок, а не обрыв, и об этом
стоит сказать.

## 9. Управление узлом без выкатки

**Зачем.** Обе кнопки нужны именно тогда, когда доступа к машине нет.

**Перечитать железо.** Карточка узла → «Железо» → «перечитать». Агент
определяет железо один раз при запуске, поэтому карта, вернувшаяся после
пересборки драйвера, до этой кнопки не появлялась нигде. Под работающей задачей
кнопка откажет — и правильно: индексы карт у задачи считаются от этого числа.

**Перезапустить агента.** Карточка узла → «Агент» → «перезапустить». Задачи
сливаются, узел пропадает со связи на несколько секунд и возвращается сам.
Версия при этом не откатывается.

**Лог агента.** Там же, «показать». Всё, что узел знает о туннелях и соседях —
то есть ровно то, чего не видно ниоткуда, когда машина чужая.

---

## Что из этого складывается

Сценарии 1–5 — заявка кластера целиком: он собирается между машинами за NAT,
обе считают, библиотеки клиента приезжают, данные ходят с измеримой скоростью,
и клиент может связать узлы своим кодом.

Сценарий 6 очерчивает границу, 7 показывает, что за ней всё равно есть рабочий
путь.

Сценарии 8 и 9 — про то, что этим можно пользоваться неделями, а не показать
один раз.
