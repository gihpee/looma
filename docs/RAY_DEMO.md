# Проверка кластера: девять сценариев

Порядок не случаен. Каждый следующий опирается на то, что подтвердил
предыдущий, и первое же расхождение отсекает половину возможных причин. Если
времени мало — сценарии 1, 2 и 5 дают костяк: кластер собрался, обе машины
считают, данные между ними ходят.

Скрипты кладутся в форму «точка входа» на странице Ray. Запускается такой
скрипт **только на ранге 0** — остальные ранги держат свои узлы; так и
задумано, потому что `ray.init()` на ранге 0 распоряжается всем кластером.
Результат смотреть в логе задачи ранга 0.

Где нужны карты, это сказано отдельно. Остальное считается и на процессоре.

> **Имена в коде — только латиницей.** Ray кодирует имя задачи в ASCII, и
> `@ray.remote` над функцией с кириллическим именем роняет воркер на
> `UnicodeEncodeError`. На строки и комментарии это не распространяется.

## Пролог, общий для всех скриптов

Дальше он подразумевается вставленным в начало. Две вещи в нём не
косметические.

```python
import ray
# Явным импортом: одного `import ray` для этого подмодуля не хватает, и
# обращение через ray.util.… падает с AttributeError.
from ray.util.scheduling_strategies import NodeAffinitySchedulingStrategy

ray.init()


def on(node_id):
    """Положить задачу именно на этот узел, а не куда решит планировщик."""
    return NodeAffinitySchedulingStrategy(node_id=node_id, soft=False)


def nodes_by_rank():
    """Узлы в порядке рангов.

    Через адреса, а не через порядок ray.nodes(): тот ничем не задан, и
    «первый в списке» — это не голова, а как повезёт. Зато адрес ранга N по
    построению равен 127.0.0.<N+2> и означает одно и то же на всех машинах.
    """
    alive = {n["NodeManagerAddress"]: n["NodeID"]
             for n in ray.nodes() if n["Alive"]}
    ordered = [alive.get(f"127.0.0.{2 + rank}") for rank in range(len(alive))]
    if None in ordered:
        raise SystemExit(f"узлы записаны не своими адресами: {sorted(alive)}")
    return ordered
```

Последняя проверка полезна сама по себе: если она сработала, на узле старый
payload, и остальное можно не запускать.

## 1. Кластер собрался и держится

**Зачем.** Пока это не подтверждено, любая другая неудача может оказаться этой.

**Как.** Поднять кластер из двух узлов без скрипта. В логе каждого ранга
дождаться:

```
ранг N/2 в кластере, узлов 2, голова 127.0.0.2:NNNNN
узлы в кластере: <id> 127.0.0.2:NNNNN alive=True; <id> 127.0.0.3:NNNNN alive=True
```

**Что смотреть.** Оба адреса из `127.0.0.x`. Если там `192.168.*` или `10.*` —
узел записался адресом своей локальной сети, недостижимым с чужой машины, и
через полминуты голова объявит его мёртвым.

**Через десять минут** открыть консоль ещё раз: в группе по-прежнему два узла.
Кластер разваливался именно так — собирался, а через тридцать секунд терял
узел.

## 2. Обе машины действительно считают

**Зачем.** «Кластер собрался» и «работа раскладывается по узлам» — разные
утверждения. Второе и есть то, за что платит клиент.

```python
import collections
import os
import socket
import time

print("ресурсы кластера:", ray.cluster_resources())


@ray.remote(num_cpus=1)
def whoami(_):
    time.sleep(1)          # иначе всё успеет лечь на первый освободившийся узел
    return socket.gethostname(), os.environ.get("LOOMA_RANK")


spread = collections.Counter(ray.get([whoami.remote(i) for i in range(20)]))
for node, count in spread.items():
    print(f"{node}: {count} задач")
```

**Что смотреть.** В `cluster_resources()` — `CPU` как сумма долей обоих узлов.
`GPU` появится, только если в форме указано «карт на ранг» больше нуля. В
разбивке — оба узла.

**Если всё на одном узле.** Сравните доли CPU: если одному досталось заметно
больше, планировщик честно сложит работу туда. Запустите задач больше, чем
ядер у одного узла.

## 3. Окружение через консоль

**Зачем.** Это основной способ: одно окружение на узел, поставленное **до**
запуска Ray и общее для всего кластера.

**Как.** В форме, поле «библиотеки», столбиком:

```
numpy
```

```python
@ray.remote
def probe():
    import os
    import sys

    import numpy
    return os.environ.get("LOOMA_RANK"), numpy.__version__, sys.version.split()[0]


for rank, version, python in ray.get(
        [probe.options(scheduling_strategy=on(node)).remote()
         for node in nodes_by_rank()]):
    print(f"ранг {rank}: numpy {version}, python {python}")
```

**Что смотреть.** Строка на каждый узел, версия одна и та же.

**Свойства этого способа.** Ставится один раз и кэшируется на узле: второй
кластер с теми же требованиями поднимется сразу. Доступно всему, что на узле
запускается. Меняется только пересозданием кластера.

**Если `ModuleNotFoundError`** — библиотека не доехала до этого узла; смотреть
лог его задачи на стадии установки окружения.

## 4. Окружение через `ray.init(runtime_env=...)`

**Зачем.** Второй способ, и он про другое: менять зависимости, не трогая
кластер. Полезно, когда кластер арендован надолго, а библиотека нужна разная
от запуска к запуску.

Ray ставит такое окружение сам, в момент запуска задания, на каждом узле, где
окажется работа. Порт его агента мы прокидываем.

Скрипт целиком, без пролога: `ray.init()` здесь свой, а дважды подключиться
нельзя.

```python
import ray
from ray.util.scheduling_strategies import NodeAffinitySchedulingStrategy

ray.init(runtime_env={"pip": ["cowsay==6.1"]})


def on(node_id):
    return NodeAffinitySchedulingStrategy(node_id=node_id, soft=False)


def nodes_by_rank():
    alive = {n["NodeManagerAddress"]: n["NodeID"]
             for n in ray.nodes() if n["Alive"]}
    return [alive[f"127.0.0.{2 + rank}"] for rank in range(len(alive))]


@ray.remote
def speak():
    import cowsay
    import os
    return os.environ.get("LOOMA_RANK"), cowsay.get_output_string("cow", "privet")


for rank, text in ray.get(
        [speak.options(scheduling_strategy=on(node)).remote()
         for node in nodes_by_rank()]):
    print(f"--- ранг {rank} ---\n{text}")
```

Можно и точечно, не на всё задание:

```python
@ray.remote(runtime_env={"pip": ["cowsay==6.1"]})
def speak_here():
    import cowsay
    return cowsay.get_output_string("cow", "только для этой задачи")
```

**Что смотреть.** Корова с обоих узлов. Первый запуск на узле идёт заметно
дольше: Ray заводит отдельное окружение и качает пакет.

**Чем отличается от третьего сценария.**

| | консоль | `runtime_env` |
|---|---|---|
| Когда ставится | до старта Ray, один раз на узел | при запуске задания |
| Область | весь узел | задание или отдельная задача |
| Смена | пересоздать кластер | просто другой запуск |
| Первый запуск | долгий, дальше из кэша | долгий каждый раз для нового набора |
| Место на диске | кэш окружений узла | временный каталог задачи |

**Что выбирать.** Тяжёлое и постоянное (torch, cuda-колёса) — через консоль:
кэш узла для того и есть. Лёгкое и меняющееся — через `runtime_env`.

**Честно:** этот способ на стенде не проверялся; всё, что для него нужно, на
месте, но первым его запуском будет ваш. Если `runtime_env` не поднимется,
третий сценарий работает независимо от него.

## 5. Данные ходят между узлами, и вот с какой скоростью

**Зачем.** Это единственное число, по которому потом решается, поедет ли на
кластере конкретная стратегия. Всё остальное — следствия.

Требует `numpy` (любым из двух способов выше).

```python
import time

import numpy

here = ray.get_runtime_context().get_node_id()
far = next(n for n in nodes_by_rank() if n != here)


@ray.remote(scheduling_strategy=on(far))
def receive(chunk):
    return chunk.nbytes


for mb in (1, 8, 64):
    ref = ray.put(numpy.zeros(mb * 1024 * 1024, dtype=numpy.uint8))
    started = time.time()
    ray.get(receive.remote(ref))
    spent = time.time() - started
    print(f"{mb:>3} МБ за {spent:5.2f} с = {mb * 8 / spent:6.1f} Мбит/с")
```

**Что смотреть.** Число на 64 МБ — рабочая полоса между узлами. Малые куски
меряют задержку, а не полосу, и будут заметно хуже: это нормально.

**Как этим пользоваться.** Обучение модели на 7B через DDP требует около 14 ГБ
обмена **на шаг**. Поделите на полученное число — получите время шага. Вышли
минуты, значит эта стратегия здесь бессмысленна, и инженерией это не лечится.

## 6. Межузловой обмен своими руками

**Зачем.** Не всё выражается через Ray. Клиенту нужен способ связать узлы своим
кодом — для этого есть окно портов, проброшенное заранее.

Каждый ранг получает в окружении:

| Переменная | Что в ней |
|---|---|
| `LOOMA_RANK_ADDRS` | `0=127.0.0.2,1=127.0.0.3` — где какой ранг |
| `LOOMA_PORTS` | `20170-20199` — порты ЭТОГО ранга, видные соседям |
| `MASTER_ADDR` / `MASTER_PORT` | точка встречи на ранге 0 |
| `WORLD_SIZE`, `RANK`, `NODE_RANK` | размер группы и своё место в ней |

Адреса `127.0.0.x` — не локалхост в обычном смысле: у каждого ранга свой, и он
означает одно и то же на всех машинах группы. У себя за ним настоящий процесс,
на других машинах — агент с туннелем.

```python
import os
import socket
import time

addr, port = os.environ["MASTER_ADDR"], int(os.environ["MASTER_PORT"])
ranks = nodes_by_rank()


@ray.remote(scheduling_strategy=on(ranks[0]))
def listener():
    server = socket.socket()
    server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    server.bind((addr, port))      # свой адрес ранга 0, а не 0.0.0.0
    server.listen(1)
    server.settimeout(60)
    guest, _ = server.accept()
    got = guest.recv(64)
    guest.sendall(b"ok:" + got)
    return got.decode()


@ray.remote(scheduling_strategy=on(ranks[1]))
def caller():
    time.sleep(3)                  # дать слушателю встать
    sock = socket.create_connection((addr, port), timeout=30)
    sock.sendall(b"privet")
    return sock.recv(64).decode()


waiting = listener.remote()
print("гость получил:", ray.get(caller.remote()))
print("хозяин получил:", ray.get(waiting))
```

**Что смотреть.** `гость получил: ok:privet` — соединение прошло между машинами
через туннель, и клиентский код может строить на этом что угодно.

**Если соединение отвергнуто** — порт вне окна. Сверьтесь с `LOOMA_PORTS` того
ранга, который слушает. Порты вне окна прекрасно работают у себя на машине и не
видны снаружи, поэтому ошибка появляется только на двух узлах.

## 7. torch.distributed: где именно проходит граница

**Зачем.** Чтобы не выяснять это на клиенте. Граница настоящая, и она не в
нашем коде.

Требует `torch`.

### Что работает — точка встречи

`TCPStore` живёт на одном порту, и он проброшен.

```python
import os
from datetime import timedelta

import torch.distributed as dist

addr, port = os.environ["MASTER_ADDR"], int(os.environ["MASTER_PORT"])
ranks = nodes_by_rank()
DEADLINE = timedelta(seconds=60)


@ray.remote(scheduling_strategy=on(ranks[0]))
def host():
    store = dist.TCPStore(addr, port, 2, True, timeout=DEADLINE)
    store.set("hello", "from rank 0")
    return store.get("reply").decode()


@ray.remote(scheduling_strategy=on(ranks[1]))
def guest():
    store = dist.TCPStore(addr, port, 2, False, timeout=DEADLINE)
    got = store.get("hello").decode()
    store.set("reply", "from rank 1")
    return got


waiting = host.remote()
print("гость прочитал:", ray.get(guest.remote()))
print("хозяин прочитал:", ray.get(waiting))
```

Через такой склад строится параметр-сервер и любой обмен с редкой
синхронизацией.

### Что НЕ работает — коллективы между машинами

`init_process_group` с backend `gloo` или `nccl` дойдёт до точки встречи и
повиснет на первом `all_reduce`. Причина не в настройке: коллективы открывают
между рангами свои сокеты на **случайных** портах, и какой порт им достанется,
известно только после того, как они его заняли. Пробросить заранее то, что ещё
не выбрано, нельзя. Лечится это не флагом, а сетевым слоем другого рода — общим
адресным контуром на всех узлах; такого слоя сейчас нет.

**Внутри одной машины коллективы работают полностью.** Выберите один узел и
поставьте на него два ранга: там `127.0.0.1` настоящий.

**Вывод для клиента.** Между машинами — Ray-native обмен (сценарий 5) или свой
транспорт (сценарий 6). Внутри машины — что угодно.

## 8. Задача, которая не влезает в одну карту

Требует карт на обоих узлах и `torch`.

**Зачем.** Это вопрос, который задаёт каждый: «у меня 40 ГБ, а карты по 24».
Сценарий показывает и ответ, и его цену.

Ray **не** объединяет VRAM: одна аллокация CUDA не лежит на двух машинах — как
и на одной машине с двумя картами. Разрезать должна стратегия. Работающая здесь
стратегия — конвейер по слоям: между узлами едут активации, а не веса.

```python
import time

import torch


@ray.remote(num_gpus=1)
class Half:
    def __init__(self, layers, width):
        self.block = torch.nn.Sequential(*[
            torch.nn.Linear(width, width) for _ in range(layers)]).cuda().half()

    def forward(self, x):
        with torch.no_grad():
            return self.block(x.cuda().half()).cpu()


width, layers = 4096, 8
ranks = nodes_by_rank()
first = Half.options(scheduling_strategy=on(ranks[0])).remote(layers, width)
second = Half.options(scheduling_strategy=on(ranks[1])).remote(layers, width)

x = torch.randn(8, 2048, width)
started = time.time()
# Ссылка передаётся напрямую: Ray разыменует её на второй половине, и переезд
# активаций накладывается на счёт, а не ждёт его.
out = ray.get(second.forward.remote(first.forward.remote(x)))
print(f"через обе половины за {time.time() - started:.2f} с, форма {tuple(out.shape)}")
```

**Что смотреть.** Оба актора заняли по карте — значит модель размазана по двум
машинам и суммарная память использована. Время прохода включает переезд
активаций: поделите их объём на число из сценария 5 и сверьтесь.

**Чего сценарий не показывает.** Обучение. Оно добавляет обратный проход, то
есть примерно удваивает обмен. Конвейерное обучение на этом канале возможно при
большом накоплении градиента; DDP и FSDP — нет, и сценарий 5 объясняет почему.

**Честно:** из девяти этот проверен меньше остальных. Если не пойдёт, дело
скорее в torch и картах, чем в кластере, — и сценарии 2 и 3 к тому моменту это
уже разделят.

## 9. Кластер переживает нагрузку, снятие и потерю узла

**Зачем.** Аренда — это часы, а не минуты. Разваливалось оно как раз со
временем.

1. Оставить кластер под нагрузкой — например, повторять сценарий 5 по кругу.
2. Через полчаса открыть консоль: в группе по-прежнему оба узла.
3. Снять группу кнопкой. Задачи уходят в `stopped`, на машинах не остаётся
   процессов Ray.

**Что смотреть в логе агента.** Строки «туннель … прожил N с и закрылся».
Долгие соединения несущие: на них держится связь узла с головой. Если такое
закрывается регулярно через одинаковое N — это срок, а не обрыв, и об этом
стоит сказать.

**Заодно — кнопки узла.** Карточка узла → «Железо» → «перечитать»: агент
определяет железо один раз при запуске, поэтому карта, вернувшаяся после
пересборки драйвера, до этой кнопки не появлялась нигде. Под работающей задачей
кнопка откажет, и это правильно: индексы карт у задачи считаются от этого
числа. «Агент» → «перезапустить» сливает задачи и поднимает агента заново, не
откатывая версию.

## Что из этого складывается

Сценарии 1–6 — заявка кластера целиком: он собирается между машинами за NAT,
обе считают, окружение клиента приезжает двумя разными путями, данные ходят с
измеримой скоростью, и клиент может связать узлы своим кодом.

Сценарий 7 очерчивает границу, 8 показывает, что за ней всё равно есть рабочий
путь.

Девятый — про то, что этим можно пользоваться неделями, а не показать один раз.
