# Tensor parallelism внутри узла

Что изменилось в стадии vLLM, как она теперь устроена и что проверено на
стенде. Общее описание стадии — в [VLLM_STAGE.md](VLLM_STAGE.md); здесь только
то, что появилось вместе с многокарточными узлами.

## Задача

До этого стадия vLLM жила на **одной карте**: `GPUModelRunner` строился прямо в
процессе стадии, с вырожденной распределённой группой из одного ранга. На узле
с четырьмя A30 модель, не влезающая в 24 ГБ, не поднималась вовсе, а три карты
простаивали. Оркестратор при этом считал долю узла по сумме карт — и стадия
падала с OOM, пытаясь положить долю четырёх карт на одну.

Отвергнутый вариант: развернуть многокарточную машину в несколько рангов —
по стадии на карту, активации через агента. Карты одной машины связаны шиной
в сотни гигабит, а сосед по конвейеру — тоннелем в десятки мегабит; гонять
через тоннель то, что можно сложить по шине, — терять на каждом токене.

Принятая схема — **два уровня параллелизма**:

| уровень | между кем | что делится | как ходят данные |
|---|---|---|---|
| pipeline parallelism | машины | диапазон слоёв на стадию | активации через агента (тоннель) |
| tensor parallelism | карты одной машины | каждый слой поровну на все карты | NCCL по PCIe/NVLink |

Пример: узел с 2×A40 (TP=2) и два узла по одной 4090 (TP=1) — конвейер из
трёх стадий, первая из которых внутри себя TP=2. Соседи по конвейеру этого не
видят: для них стадия одна, сколько бы карт под ней ни было.

## Что изменилось

**Стадия** (`payloads/looma_stage/looma_stage/`, едет на узел с задачей —
релиз агента не нужен):

- `vllm_worker.py` — **новый**. Воркер vLLM, знающий свой срез: наследник
  штатного `vllm.v1.worker.gpu_worker.Worker`, которого vLLM строит по имени в
  каждом процессе. Все наши подмены накладываются здесь.
- `vllm_engine.py` — процесс стадии стал **драйвером без карты**:
  `StageDriver` держит менеджер блоков KV-кэша, собирает батч, рассылает его
  воркерам через штатный исполнитель vLLM и забирает результат. Память
  планируется от карты, а не от узла. Появились `card_count`, `per_card`,
  `start_executor`, `provide_compiler`, предупреждение про `/dev/shm`.
- `vllm_runner.py` — `replace_pipeline_group` подменяет класс готовой группы
  вместо постройки второй; `lay_out_cache` раскладывает кэш на все воркеры
  разом; проба спецификации кэша по обёрткам (`_kv_spec_of`) убрана — её
  спрашивает сам воркер vLLM, как в штатном движке.
- `vllm_batch.py` — `prefill` запоминает запросы, под которые выданы блоки,
  в `runner.requests`: раньше этот список вёл `GPUModelRunner`, теперь батч
  собирает драйвер, у которого исполнителя нет.

**Оркестратор** (`src/looma/orchestrator/models.py`): `expand_ranks` для vLLM
считает долю узла как `N × min(карта)`.

**Агент**: шлёт свободную память по каждой карте (`vram_free_per_gpu` в
`Hardware`, `hwinfo.free_vram_per_gpu`). Без этого оркестратор делит сумму
поровну — на узле с одинаковыми картами то же число, на разных — завышенное.

## Как это работает

### Процессы

```
                    процесс стадии (драйвер)
                    ├── HTTP/конвейер, батч, менеджер блоков KV-кэша
                    └── MultiprocExecutor (vLLM)
                          ├── VLLM::Worker_TP0  cuda:0   ─┐
                          ├── VLLM::Worker_TP1  cuda:1    │ NCCL
                          └── …                           ─┘
```

Драйвер карту **не держит**. Он:

1. собирает `SchedulerOutput` из батча, который выбрала голова конвейера
   (`vllm_batch.prefill/decode`), выдавая блоки KV-кэша из своего
   `KVCacheManager` — он один на все карты, потому что состав батча один на
   все, и блоки под него обязаны совпасть на каждой;
2. рассылает батч и входящие тензоры всем воркерам (`collective_rpc
   "stage_step"`), с таймаутом `STEP_TIMEOUT_S` — зависшая NCCL-коллектива не
   вешает стадию молча;
3. забирает ответ с ранга 0 — у остальных он тот же самый.

Воркер (по одному на карту, `tensor_parallel_size = число видимых карт`):

- грузит свой срез слоёв, порезанный по TP: каждый слой — на все карты
  поровну (`VocabParallelEmbedding`, `ColumnParallelLinear`,
  `RowParallelLinear` — штатные слои vLLM);
- держит рабочую половину KV-кэша: тензоры, связанные со слоями внимания;
- считает шаг: `StageRunner.execute_model(scheduler_output, incoming)`.

Одна карта — тот же путь с одним воркером. Отдельного «однокарточного» кода
нет, и узел с одной картой проверяет тот же код, что и узел с четырьмя.

### Как наши подмены попадают в воркер

vLLM создаёт воркеры сам, в отдельных процессах (`spawn`), и передаёт туда
ровно две вещи: имя класса (`ParallelConfig.worker_cls`) и конфиг
(`VllmConfig`). Поэтому:

- класс — `looma_stage.vllm_worker.StageWorker`; модуль отдаёт его через
  `__getattr__`, потому что базовый тип живёт в vLLM, которого на машине без
  карты нет, а модуль обязан импортироваться и там;
- срез стадии (`start_layer`, `end_layer`, `num_model_layers`) едет в
  `VllmConfig.additional_config["looma_stage"]`.

В каждом воркере, в этом порядке:

| шаг | что | где |
|---|---|---|
| заплата на загрузчик | у средней стадии законно нет `embed_tokens`/`lm_head` | `init_device`, до всего |
| `GPUModelRunner` → `StageRunner` | штатный `init_device` берёт класс по имени в модуле в момент вызова; на это время имя указывает на наш. Если версия импортирует иначе и построился обычный — замена явная, с предупреждением в логе | `init_device` |
| группа конвейера по слоям | подменяется **класс** готового объекта `_PP`, а не строится вторая группа: `new_group` — коллективный вызов, а при TP у каждого воркера свой список групп конвейера (`[[0],[1],…]`), и такой вызов повис бы на первом узле с двумя картами | `init_device`, после штатного |
| `layer_range` | `get_pp_indices` отвечает нашим диапазоном на время загрузки, возвращается через `try/finally` | `load_model` |
| проверка числа слоёв | собралось не столько, сколько просили, — отказ: подмена не сработала, воркер держит чужие слои | `load_model` |
| рабочая половина кэша | штатный `initialize_from_config` по раскладке от драйвера | по RPC |

### Шаг

```
голова:   батч ──▶ драйвер: SchedulerOutput + блоки ──▶ воркеры (все)
                                                          │ execute_model
                                                          │ TP all-reduce × 2 на слой
          ◀── ранг 0: hidden (средняя) / логиты (последняя) ◀──┘
```

- Входящие тензоры нужны **каждому** воркеру целиком: при TP вход слоя один на
  всех картах.
- Через очередь исполнителя тензоры едут **на процессоре**: CUDA-тензор через
  pickle — это IPC-дескриптор, который в чужом процессе без той же карты не
  откроется. Воркер кладёт их на свою карту сам.
- На последней стадии логиты забираются копией **до** `sample_tokens`
  (сэмплер vLLM правит их на месте), и закрывать шаг обязан **каждый** ранг —
  иначе на ранге 1 упадёт следующий, а ответ читается с нулевого, и причины по
  нему не видно.
- Токен выбираем сами, тем же кодом, что и переносимый движок: один и тот же
  промпт даёт один ответ на обоих.

### Память

Планируется **от карты**, потому что доля vLLM (`gpu_memory_utilization`)
одна на все карты и применяется к каждой:

| что | как делится |
|---|---|
| веса | на все карты поровну |
| KV-кэш на токен | по KV-головам: `min(карт, голов)`. Когда карт больше, чем голов (GQA на восьми картах), vLLM головы дублирует |
| квота узла от оркестратора | поровну на карту |
| «размер карты» | самая маленькая из видимых |

Раскладка кэша одна на всех воркеров: место берётся по той карте, где свободно
меньше всего (`lay_out_cache`).

Оркестратор считает долю узла как **`N × min(карта)`**: TP режет каждый слой
поровну, и меньшая карта задаёт предел всем. На 24+12 ГБ стадия возьмёт 2×12,
а не 36. Отсюда же разрез модели между узлами: узел 2×24 против узла 1×24
получит 2/3 слоёв.

### Уборка

`VllmEngine.shutdown` → `LoadedShard.close` → `executor.shutdown()`: воркерам
закрывают «пайп смерти», потом SIGTERM, потом SIGKILL. Если стадия упала на
подъёме после того, как воркеры уже держат карты, `load_shard` закрывает их
сам. Запасной путь — агент: воркеры наследуют `LOOMA_TASK_ID`, и снятие задачи
убивает их по маркеру вместе со всем остальным.

## Ловушки со стенда

**`Failed to find C compiler` на первом шаге.** Две модели, одна причина:
на узле нет C-компилятора, а Triton при первом запуске любого своего ядра
компилирует маленький C-модуль (`cuda_utils`).

- Qwen3 при TP=2: `VocabParallelEmbedding.forward` при `tp_size > 1` зовёт
  `get_masked_input_and_mask` под `@torch.compile(backend="inductor")`;
  inductor генерирует Triton-ядро. На одной карте ветка не выполняется —
  потому раньше не всплывало. Сначала это закрыли запретом torch.compile
  (`TORCH_COMPILE_DISABLE=1`) — работало, но лечило симптом.
- gpt-oss-20b (MoE + attention sinks): Triton зван напрямую — маршрутизация
  экспертов (`fused_moe/gpt_oss_triton_kernels_moe.py`) и внимание с sinks на
  картах без FlashAttention-3 (`TRITON_ATTN`) в vLLM 0.14 реализованы только
  Triton-ядрами. Запрет torch.compile здесь бессилен.

Лечение одно на оба случая и без правки образа агента: в окружение vLLM
ставится pip-пакет `ziglang` (`zig cc` внутри, ~90 МБ; `TRITON_COMPILER` в
оркестраторе), стадия пишет обёртку `looma-cc` в свой scratch и ставит `CC`
до подъёма воркеров (`provide_compiler`). Запрет torch.compile после этого
снят. Проверено на nv3: `cuda_utils` Triton собирается. Подробности, риски и
запасной вариант (`gcc` в образ агента) — в
[warning/triton-compiler.md](../warning/triton-compiler.md).

**`/dev/shm`.** Очереди исполнителя живут там: кольцо драйвер→воркеры
10×16 МБ, ответ каждого воркера 10×24 МБ. В контейнере по умолчанию 64 МБ.
Кончается не при создании, а при первой записи за край — воркер умирает по
SIGBUS без строки в логе. Стадия предупреждает на подъёме и называет
`--shm-size`; это предупреждение, а не отказ: мелкие батчи укладываются.

**`WorkerProc initialization failed… see stack trace`.** Так исполнитель
сообщает о любом отказе воркера; причина — в логе самого воркера выше по
выводу (строки `WorkerProc failed`), они пишут в тот же stderr.

## Что проверено на стенде

Qwen3-4B, bf16:

| сценарий | результат |
|---|---|
| один узел, 2 карты (TP=2) | поднялась, `VLLM::Worker_TP0/TP1` по 12.3 ГБ на своих картах, отвечает |
| два узла по одной карте (чистый PP, как раньше) | работает, 17–18 ток/с |
| два узла: 2 карты + 1 карта (TP=2 внутри PP) | работает, 16–17 ток/с |

Разница в 3–4 мс на токен между вторым и третьим — цена TP при decode на
маленькой модели, и она ожидаема:

- **2 all-reduce на слой** (после attention out-proj и MLP down-proj); у узла
  с двумя картами ~24 слоя → ~48 коллективов на токен. Тензор при decode
  крошечный (5 КБ), так что это чистая латентность NCCL по PCIe, 20–50 мкс
  каждая → 1–2 мс;
- хоп драйвер↔воркеры через очередь, ~0.5–1 мс;
- шаг длится по самому медленному воркеру.

Экономия от TP при этом — половина чтения весов: ~4 ГБ на токен на одной A30
это ~4 мс, на двух ~2 мс. Против 2–4 мс накладных — около нуля. Весь шаг
при этом ~55–60 мс, и почти всё это тоннель между узлами: сдвиги внутри узла
видны как единицы миллисекунд на его фоне.

TP даёт плюс там, где счёт на токен большой: модель, не влезающая в одну
карту (ради чего всё и сделано), длинный prefill, батч из нескольких
запросов. На 4B при batch=1 decode делить нечего.

## Чего ещё нет

- **захват CUDA-графов** — `enforce_eager`; при TP цена запуска ядер
  умножается на число воркеров, честный прогрев вернул бы часть;
- **NVLink** — ничего не настраивается, NCCL возьмёт его сам, если мост есть;
  по PCIe all-reduce заметно дороже;
- **ёмкость конвейера** — голова знает число мест только своей стадии;
  у стадии с TP мест может быть больше или меньше, чем у соседа;
- **учёт карт агентом** — стадия просит `gpus=0`, и агент карты не
  резервирует; TP берёт все видимые, так что две стадии на одном узле сейчас
  поделят карты только через `CUDA_VISIBLE_DEVICES`, который агент выставляет
  лишь при явном запросе карт.
