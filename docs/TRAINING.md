# Дообучение LoRA по конвейеру

Что уже есть (фаза 1 — ядро), как оно устроено и что дальше. План целиком и
решения, которые к нему привели, — в разговоре от 2026-09-17; коротко:

- **один код для любого числа стадий** — конвейерный тренер свой, LLaMA-Factory
  и `transformers.Trainer` не используются (у них нет цикла с сетью между
  forward и backward);
- модель, адаптеры, autograd — чужие (transformers, torch); наше — цикл и то,
  чем стадия отличается в режиме обучения;
- методы: SFT сейчас, DPO следующим; точность базы (bf16 / NF4) — выбор
  клиента, не архитектуры.

## Устройство

```
голова (стадия 0)                    стадии 1..N-1
├ датасет → токены, метки            ├ срез слоёв + LoRA + оптимизатор
├ embed + слои [0,a) + LoRA          ├ графы микробатчей в полёте
├ микробатчи, GPipe                  └ последняя: norm, lm_head, loss,
├ норма градиента → коэффициент         первый backward
│  обрезки на всех
└ сборка адаптера
        ▲──── train_forward / train_backward / train_norm / train_step /
              train_save / train_collect — словари через batch_wire ────▲
```

Пакет `payloads/looma_stage/looma_stage/train/`:

| файл | что |
|---|---|
| `lora.py` | адаптеры на срезе (свой `LoRALinear`: база заморожена, `A`/`B` в float32), сохранение и чтение в формате **PEFT** под глобальными именами слоёв, слияние кусков от стадий |
| `forward.py` | батч с паддингом и маской через срез; маска `[B,1,S,S]` аддитивная, строится нами (слои зовутся напрямую); пересчёт активаций по слоям |
| `stage.py` | `TrainStage`: `forward` (первая — от токенов, прочие — от активаций как листа графа), `backward` (граф держится по `(batch_id, micro)` до прихода градиента), `grad_norm_squared`, `step(lr, grad_scale)`, `save`/`load`, `adapter_piece` |
| `data.py` | JSONL `{"messages": […]}` → токены через шаблон чата токенизатора; метки `-100` на промпте (граница — общий префикс промпта и полного диалога); `collate` с паддингом справа; батчи из микробатчей |
| `transport.py` | протокол сообщений и `handle(stage, message)`; `LocalTransport` — стадии в одном процессе, тензоры всё равно через провод |
| `head.py` | `Trainer`: GPipe (все микробатчи вперёд, все назад, один шаг), доля микробатча в loss, общая норма градиента по всем стадиям и один коэффициент обрезки, lr с разогревом и линейным затуханием, чекпоинты, `collect_adapter` |

Ключевые решения, каждое проверено тестом:

- **Градиенты весов между узлами не ходят** — только градиенты активаций,
  того же размера, что активации. Адаптеры слоя лежат там же, где слой.
- **Обрезка нормы — глобальная**: стадии отдают квадраты своих норм, голова
  считает корень из суммы и шлёт один коэффициент. Иначе результат зависел
  бы от того, на сколько стадий порезана модель.
- **Loss микробатча взвешен долей его токенов** в батче, чтобы градиент
  сложился в среднее по батчу, а не в сумму средних.
- **Граница между стадиями — настоящая даже в одном процессе**: тензоры
  проходят `wire`, граф не разделяется. Поэтому CPU-тест на одном процессе
  ловит то, что сломалось бы на двух машинах.

## Что проверено (без карты)

`tests/test_train_pipeline.py`: крошечная Llama (4 слоя) как настоящий
чекпоинт на диске →

- конвейер из **двух** и из **трёх** стадий даёт тот же loss и те же адаптеры
  после шагов, что одна стадия с целой моделью (float32, `atol=1e-6`);
- пересчёт активаций не меняет результат;
- паддинг не влияет: пример в одиночку и он же рядом с длинным соседом дают
  тот же вклад в loss;
- на выучиваемых данных loss падает;
- наш адаптер читается `peft.PeftModel.from_pretrained` на целую модель и
  считает то же, что наш срез (это же гарантирует vLLM `--lora-modules`);
- чекпоинт стадии восстанавливается (адаптеры + оптимизатор + шаг);
- отказы: шаг при микробатчах в полёте, backward без forward, роли.

`tests/test_train_data.py`: граница loss по шаблону, обрезка, JSONL, склейка.

## Как это едет по узлам (фаза 2)

```
веб «Обучение» ──▶ POST /admin/train ──▶ группа задач, engine=train
                                          ├ входы: код стадии + train.json + train.jsonl
                                          ├ команда: looma_stage.server --engine train
                                          │          --train-config train.json …
                                          └ запись в training_jobs (Postgres) или в памяти
     GET /admin/train/{id} ◀── progress.json из результатов головы (agents.collect)
     результат: /admin/tasks/<голова>/results/adapter/…
```

**Стадия** (`server.py --engine train`, `train/run.py`): `TrainingRun` живёт в
`STATE["train"]`; сообщения `train_*` сервер отдаёт ему как есть. Голова
ведёт `Trainer` через `ChannelTransport` — стадия 0 в процессе, остальные за
`relay` с ответом `train_reply` по `call_id`; перед первым микробатчем
`wait_ready` пробует стадии короткими `train_ping`, потому что сообщение,
пришедшее до готовности, стадия отбрасывает. Ошибка стадии едет текстом в
`train_reply` — голова узнаёт причину сразу, а не по таймауту. Сообщения
крупнее `PART_BYTES` (1 МБ) едут кусками `train_part` и собираются у
получателя (`transport.parted`/`Parts`): кусок адаптера стадии — десятки
МБ, а gRPC-канал агента принимал 4 МБ и молча ронял такое (со стенда:
два узла, 40 шагов прошли, `train_collect` ждал 600 с). Прогресс —
`out/progress.json` (атомарно, последние 500 шагов), результат —
`out/adapter/` + `out/result.json`. Голова выходит с кодом 0 после сборки
адаптера (1 — если упала) и говорит остальным `train_finish`; для агента
это обычная задача, которая кончилась.

**Оркестратор** (`/admin/train`): `describe` модели (теперь с размерами
слоёв и `quantization_config`), отказ квантованным чекпоинтам, выбор узлов
как у деплоя, `split_layers` по памяти, **оценка памяти на стадию**
(`training_stage_bytes`: веса среза в выбранной точности + адаптеры и
оптимизатор в float32 + активации `m` микробатчей + логиты последней +
запас) — не влезает → 409 с числами по стадиям и подсказкой (`nf4` /
больше узлов / `force=true`). Датасет — JSONL в base64, до 64 МБ. Записи —
`training_jobs` (миграция `0004_training.sql`, `usage/training.py`;
без базы — в памяти). `GET /admin/train[/{id}]` сводит состояние по
`progress.json` головы и закрывает запись по её исходу; `/stop` снимает
группу.

**Веб**: вкладка «Обучение» — форма (модель, JSONL, точность, узлы,
«подробно»: r/alpha/dropout/lr/эпохи/разогрев/батч/микробатч/длина),
карточки заданий с прогрессом, кривой loss, ETA, ток/с, ошибкой и кнопками
скачать адаптер (через токен, не ссылкой).

Попутно починено в `agents.py`: ответ узла на `collect`/`logs` завершал
ожидание из чужого цикла (тесты HTTP крутят приложение в своём потоке), и
ждущий узнавал о нём только по своему таймауту — `collect` возвращал
правильный ответ ровно через 120 с. Теперь `_settle` будит нужный цикл.

## Адаптер в инференс (фаза 4)

```
обучение done ──▶ оркестратор забирает adapter/ с головы ──▶ <data_dir>/adapters/<group_id>/
                  (в момент сводки или свипером раз в 30 с;    adapter_config.json
                   результат на узле живёт час)                 adapter_model.safetensors, meta.json
POST /admin/deploy {repo, adapter: <group_id>, engine} ──▶ стадии: входы + adapter/…, флаг --adapter adapter
```

- **Оркестратор**: `orchestrator/adapters.py` — `AdapterStore` на диске (адаптер
  8B при r=16 — под 200 МБ, в базе ему не место); `_keep_adapter` при переходе
  обучения в `done`, `sweep_training` в сервере — чтобы адаптер забрался и
  без открытой вкладки. Скачивание — `GET /admin/train/{id}/adapter/{файл}`,
  уже от оркестратора. `deploy` с `adapter` проверяет, что база та же, на
  которой учили (адаптер считан под её размеры и имена), кладёт файлы во
  входы и даёт имя `база+адаптер`.
- **Стадия** (`--adapter <каталог>`): torch — `lora.merge_into` вплавляет
  `α/r·B·A` в веса среза (без модулей LoRA в графе, без лишнего умножения;
  проверено против `peft` на срезе из двух стадий); vLLM — штатный LoRA:
  `LoRAConfig(max_lora_rank=r↑, max_loras=1)` в конфиг, `LoRARequest` в каждый
  запрос (`vllm_batch`), воркер грузит адаптер с диска при первом запросе.
  Имена в адаптере глобальные, а слои у vLLM с `get_pp_indices` тоже глобальные,
  так что один файл читает каждая стадия, лишние слои пропускаются.
- **Веб**: в карточке обучения «развернуть» (форма развёртывания с
  подставленными адаптером и базой); в форме на «Моделях» — выбор адаптера
  из готовых. Дальше — обычная модель: «спросить» в чате.

## Чего пока нет

- **NF4 на стенде** — код есть (`train/run.py::_quantize`, `bitsandbytes`
  ставится при `precision=nf4`), но на карте не проверен: `bitsandbytes` —
  только CUDA.
- **Стенд для конвейера**: один узел проверен (2026-09-18, Qwen3-0.6B bf16,
  `examples/train/demo.jsonl`: 40 шагов, loss 3.76 → 0.19, 249 ток/с на nv3;
  адаптер через `peft` меняет ответы — `examples/train/check_adapter.py`).
  Дальше nf4 на том же узле, потом два узла и 8B/32B; обрыв узла →
  возобновление с чекпоинта (стадии пишут `checkpoints/step-N`,
  автоматического возобновления пока нет).
- **1F1B** вместо GPipe, сжатие активаций на проводе, упаковка коротких
  примеров, DPO, DP-ось для LoRA, датасеты больше 64 МБ по URL.

Агент не затронут: обучение — группа задач с python-окружением, как стадии
инференса.
