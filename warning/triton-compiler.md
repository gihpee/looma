# C-компилятор для Triton приезжает pip-пакетом `ziglang`

Дата: 2026-09-17. Затронуто: `src/looma/orchestrator/models.py`
(`TRITON_COMPILER`), `payloads/looma_stage/looma_stage/vllm_engine.py`
(`provide_compiler`). Образ агента не менялся.

## Что случилось

Два падения на стенде с одним текстом — `Failed to find C compiler. Please
specify via CC environment variable or set triton.knobs.build.impl`:

1. Qwen3-4B, один узел, TP=2. vLLM при `tp_size > 1` зовёт в
   `VocabParallelEmbedding` функцию под `@torch.compile(backend="inductor")`,
   inductor генерирует Triton-ядро.
2. gpt-oss-20b, тот же узел. Triton зван напрямую: маршрутизация экспертов
   (MoE) и внимание с attention sinks на картах без FlashAttention-3 (всё,
   что не Hopper) в vLLM 0.14 реализованы только Triton-ядрами.

Причина одна: **Triton при первом запуске любого своего ядра компилирует
маленький C-модуль (`cuda_utils`) и ищет `$CC`, `gcc` или `clang`**. В
образе агента (`python:3.12-slim`) компилятора нет — намеренно, образ тонкий.
Плотные модели на одной карте на Triton не заходят, поэтому месяцами не
всплывало.

Первое падение сначала закрыли запретом `torch.compile`
(`TORCH_COMPILE_DISABLE=1`). Это лечило симптом: против второго случая
бесполезно. Запрет снят.

## Что сделано

- В требования окружения vLLM добавлен `ziglang==0.16.0` — pip-колесо
  (~90 МБ), внутри которого `zig cc`, clang-совместимый C-компилятор. Ставится
  в venv задачи как обычный пакет; отпечаток окружения меняется, узлы
  пересобирают venv при первом запуске vLLM после выката.
- Стадия vLLM перед подъёмом воркеров (`provide_compiler`): если `$CC`,
  `gcc` или `clang` уже есть — ничего не делает; иначе пишет в свой
  scratch-каталог обёртку `looma-cc` (`exec <python задачи> -m ziglang cc
  "$@"`) и ставит `CC` на неё. Воркеры наследуют окружение. Если `ziglang`
  не установлен — предупреждение в лог, плотные модели работают как раньше.
- Проверено на nv3 (4×A30, cu128): `cuda_utils` Triton собирается zig'ом с
  одним безобидным предупреждением (`_POSIX_C_SOURCE` redefined). gpt-oss-20b
  после этого — на проверке.

## Почему это предупреждение, а не просто фича

`zig cc` — не `gcc`. Официальный образ vLLM и все остальные ставят `gcc`; наш
путь нестандартный, и вот где он может сломаться:

- **Заголовки.** `cuda_utils.c` включает `Python.h` (есть в `python:3.12-slim`
  по адресу `/usr/local/include/python3.12`) и `cuda.h` из комплекта Triton.
  Если базовый образ сменится на такой, где Python-заголовков нет, — сборка
  упадёт. Симптом: `Python.h: No such file`.
- **Линковка с `libcuda`.** Triton передаёт `-L<каталог libcuda> -lcuda`; zig
  линкует ELF сам. Работало на cu128; на другом драйвере/дистрибутиве
  теоретически может не найти `libcuda.so`. Симптом: `unable to find library
  -lcuda`.
- **Inductor на CPU.** Если vLLM когда-нибудь скомпилирует что-то не для
  карты, inductor захочет `g++` (C++), а не `cc`. У zig есть `zig c++`, но
  наша обёртка даёт только `cc`. Симптом: ошибка из
  `torch._inductor.cpp_builder` про компилятор.
- **Версия Triton.** Сборка `cuda_utils` — внутренний механизм Triton; смена
  torch (а значит Triton) при смене `VLLM_PIN` может поменять флаги
  компиляции. Проверять при каждом поднятии пина.
- **Место и время.** +90 МБ в каждом окружении vLLM на каждом узле; первый шаг
  каждой задачи на несколько секунд дольше (кэш Triton `~/.triton` лежит в
  каталоге задачи и умирает с ней).

## Проверено 2026-09-17: zig не виноват в качестве

На nv3 в живой контейнер поставили `gcc` (`apt-get install gcc libc6-dev`),
перезапустили gpt-oss-20b — `provide_compiler` взял `gcc` из PATH, кэш Triton
пересобрался им. Каша в ответах осталась той же; причина оказалась в нашем
сэмплере (см. docs/TENSOR_PARALLEL.md, «Выпавшие слоги»). То есть лаунчеры,
собранные zig'ом, работают так же, как собранные gcc, — риск из списка выше
на этом стенде не подтвердился. На nv3 gcc теперь есть в контейнере до
следующего обновления образа; остальные узлы на zig.

## Запасной вариант A — `gcc` в образ агента

Одна строка в `agent/Dockerfile`:

```dockerfile
RUN apt-get update && apt-get install -y --no-install-recommends gcc libc6-dev \
    && rm -rf /var/lib/apt/lists/*
```

+~90 МБ к образу. Это то, как устроен официальный образ vLLM, и это
«правильный» компилятор без оговорок выше. Цена — **изменение образа**, а не
релиз агента: владельцы узлов делают `docker pull` руками, и Dockerfile
написан так, чтобы этого не случалось.

**Когда переходить на A:** если любой из симптомов выше воспроизведётся на
узле, где `gcc` решил бы дело; если у части узлов сборка zig'ом окажется
нестабильной; или если образ всё равно придётся перевыкатывать по другой
причине — тогда логично положить `gcc` заодно и убрать `ziglang` из
требований (`provide_compiler` сам увидит `gcc` в PATH и обёртку писать не
будет — код менять не нужно).

**Проверить заранее, не дожидаясь поломки:** на одном узле собрать образ с
`gcc`, снять `ziglang` из требований и прогнать те же три сценария
(Qwen3 TP=2, gpt-oss-20b TP=2, конвейер из двух узлов). Если всё проходит —
решение о переходе чисто эксплуатационное (готовы ли владельцы обновлять
образ).
